## Continued, settlement engine: idempotency, explain-back and versioning question

Came back from a break and gave a second, more complete explain-back cold, before rereading
the rewritten article: correctly restated the client-generated key concept, the atomic
write of key and settlement data in one transaction, the storage-for-consistency trade-off,
and the insert race resolved by the unique constraint. Also produced a description of a
second concurrency problem independently, without being walked through it again, though the
mechanism described (a failed transaction's slow rollback blocking the successful one) was
not quite the real one.

Two inaccuracies found on verification against the actual code, not assumed from memory of
the earlier walkthrough:

- The claim that an in-progress retry reads a response from a database snapshot is wrong.
  `handleExisting` throws `SettlementInProgressException` when status is `IN_PROGRESS`; the
  `responseSnapshot` column is null until `complete()` runs, which happens exactly once, at
  finalize time. Only a `COMPLETED` key has anything to read back.
- The second race was described as one transaction waiting on another's rollback. The real
  mechanism, confirmed in the code, is a genuine deadlock: the winner's
  `UPDATE idempotency_keys` and a loser's `INSERT INTO settlements` (which takes a
  `FOR KEY SHARE` lock on the referenced row during FK validation) end up wanting each
  other's locks, Postgres's deadlock detector finds the cycle, and kills one side, which
  is what the bounded five-attempt retry catches.

Two new questions were asked and answered after checking the actual domain code, not
before: whether an optimistic-locking version column could solve the concurrency races, and
how Go and Postgres generally handle concurrency.

On versioning: confirmed `@Version` already exists in this codebase, on `LedgerAccount`, not
on `IdempotencyKey`. It solves lost updates on a row already read, which is the ledger
balance's problem, not idempotency's. Neither race here is a lost-update problem: race one
is about who gets to create a row first, which the unique constraint already handles
correctly, and race two is a genuine cross-table lock-ordering deadlock that a version
column would not change, since it doesn't alter what locks get taken during FK validation.
Versioning `IdempotencyKey` would solve a problem the code doesn't currently have.

On Go and Postgres: Postgres uses MVCC, each transaction sees its own snapshot, writers
block writers on the same row rather than readers blocking writers, and a background
deadlock detector kills one side of any lock cycle it finds, exactly the mechanism behind
race two. Go's concurrency model, goroutines and channels, governs coordination inside one
process and has no bearing on how Postgres locks rows; a Go rewrite of this service would
keep both races, since they live in the database's locking behavior, not the application
language.
